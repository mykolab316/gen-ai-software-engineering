# Transaction Processing Pipeline — Specification

> Author: Mykola Bernadskyi
> Generated by the `/write-spec` skill (Agent 1). Grounded in `agents.md` and
> `sample-transactions.json`.
>
> **Revision (microservices):** each pipeline agent now runs as its **own REST
> microservice**. The **execution order and service endpoints are configuration**
> (`pipeline-config.json`), which the orchestrator reads and then calls each
> agent over **HTTP**. The file-based `shared/` hand-off is preserved as the
> audit trail. A one-shot **`demo.sh`** starts every service, runs the pipeline,
> and tears it all down.

---

## 1. High-Level Objective

Process raw bank transactions through a chain of **independent agent
microservices** — validation, fraud scoring, and settlement — invoked over HTTP
in an order defined by configuration, persisting every hop as a JSON envelope in
`shared/` and the final outcomes in `shared/results/`.

---

## 2. Mid-Level Objectives

Each objective is concrete and testable:

1. **Validation gate** — a transaction is accepted only if it has all required
   fields, a parseable non-zero `Decimal` amount (negative permitted **only**
   for `transaction_type == "refund"`), and an ISO 4217 currency code.
   Everything else is `rejected` with a human-readable `reason`
   (e.g. TXN006 `XYZ` → `"currency 'XYZ' is not a valid ISO 4217 code"`).
2. **Multi-signal fraud scoring** — the fraud agent produces a `risk_score` in
   `[0.0, 1.0]` from additive signals — high value (abs amount > **$10,000**),
   off-hours (00:00–05:00 UTC, e.g. TXN004 at 02:47), cross-border
   (`country != "US"`), and `wire_transfer` — and sets `status = "flagged"`
   when the score ≥ **0.5** (e.g. TXN002 $25k, TXN005 $75k).
3. **Settlement** — every non-rejected transaction gets a 0.5% fee and a net
   amount computed with `Decimal` + `ROUND_HALF_UP`; flagged transactions still
   settle but retain their flag. Rejected records are never settled.
4. **Agents as microservices** — each agent runs as its own FastAPI service
   exposing `POST /process` (record in → record out) and `GET /health`. Services
   never call each other; only the orchestrator calls them.
5. **Configuration-driven order** — `pipeline-config.json` lists the agents with
   their names, URLs, and ports. The orchestrator reads this file and calls the
   services **in the listed order**. Reordering or repointing an agent requires
   **no code change**.
6. **Preserved audit trail** — every hop writes a valid JSON envelope into
   `shared/` (`input → processing → output → results`), and each call emits an
   audit line with an ISO 8601 timestamp, agent name, transaction ID, and
   outcome. PII (account numbers) is never logged in plaintext.
7. **One-shot demo** — `./demo.sh` starts all agent services, waits for their
   `/health`, runs the full pipeline over HTTP, prints the summary, and stops
   the services — with **zero manual steps**.

## 3. Implementation Notes

- **Monetary values:** parse amounts from their string form into
  `decimal.Decimal`. Never use `float` for amount, fee, or net. Round monetary
  results `ROUND_HALF_UP` to 2 dp.
- **Currency codes:** validate against an ISO 4217 allow-list (USD, EUR, GBP,
  JPY, …; extendable). Reject anything else.
- **Timestamps:** ISO 8601 in UTC with a trailing `Z`. Parse for the off-hours
  fraud signal.
- **Logging / audit trail:** one structured line per agent per transaction —
  `timestamp | stage | transaction_id | outcome`. Each service logs locally, and
  the orchestrator also logs each hop so a single terminal shows the whole
  distributed run. Mask PII: log `ACC-1***`, never full account numbers or names.
- **PII:** `source_account`, `destination_account`, and name-like fields are
  sensitive. They flow through the pipeline data but must not appear in logs.

- **Agent service contract:** every agent is a FastAPI app wrapping the existing
  pure function `process_transaction(record: dict) -> dict`:

  | Method | Path | Body | Returns |
  |--------|------|------|---------|
  | `POST` | `/process` | transaction record (JSON) | updated record (JSON) |
  | `GET` | `/health` | — | `{"status": "ok", "agent": "<name>"}` |

  The business logic stays in `pipeline/*.py`; a service is only a thin HTTP
  wrapper (`services/base.py::create_agent_app`). Agents remain **pure and
  idempotent-safe**: rejected records pass through untouched.

- **Configuration (`pipeline-config.json`):** the order is data, not code.

  ```json
  {
    "agents": [
      { "name": "validator",      "url": "http://localhost:8001/process", "port": 8001, "module": "services.validator_service:app" },
      { "name": "fraud_detector", "url": "http://localhost:8002/process", "port": 8002, "module": "services.fraud_service:app" },
      { "name": "settlement",     "url": "http://localhost:8003/process", "port": 8003, "module": "services.settlement_service:app" }
    ],
    "timeout_seconds": 10
  }
  ```

- **Orchestrator transport:** `call_agent(agent, record)` POSTs the record to the
  agent's URL with `httpx` and returns the updated record. A connection failure
  raises `AgentUnreachableError` with a message telling the user to start the
  services (or run `demo.sh`). Tests monkeypatch `call_agent` to dispatch
  in-process, so the suite is hermetic.

- **File-based hand-off envelope:** the orchestrator persists each hop; agents
  never read or write `shared/` themselves.

  ```json
  {
    "message_id": "uuid4-string",
    "timestamp": "2026-03-16T10:00:00Z",
    "source_stage": "validator",
    "target_stage": "fraud_detector",
    "message_type": "transaction",
    "data": {
      "transaction_id": "TXN001",
      "amount": "1500.00",
      "currency": "USD",
      "status": "validated"
    }
  }
  ```

## 4. Context

### Beginning state
- `sample-transactions.json` — a list of 8 raw transaction records:

  | Field | Type | Notes |
  |-------|------|-------|
  | `transaction_id` | string | e.g. `TXN001` |
  | `timestamp` | ISO 8601 string | UTC, `Z` suffix |
  | `source_account` | string | PII — do not log |
  | `destination_account` | string | PII — do not log |
  | `amount` | string | parse to `Decimal` |
  | `currency` | string | ISO 4217 |
  | `transaction_type` | string | `transfer` \| `wire_transfer` \| `refund` |
  | `description` | string | free text |
  | `metadata` | object | `channel`, `country` |

  Edge cases: invalid currency (`XYZ`, TXN006), negative refund (`-100.00`,
  TXN007), high-value wires (TXN002, TXN005), a boundary amount just under $10k
  (TXN003, `9999.99`), and an off-hours cross-border record (TXN004).
- `pipeline-config.json` — agent order and endpoints.

### Ending state
- Every transaction has a result file in `shared/results/` with its final
  `status` (`settled` / `flagged` / `rejected`), `risk_score`, settlement
  figures, and a `reason` when rejected.
- A **summary report** (counts by status + rejection/flag reasons) is written to
  `shared/results/_summary.json`, served by the API, and exposed as the MCP
  `pipeline://summary` resource.
- `./demo.sh` runs end-to-end with no manual steps.
- Test coverage **≥ 90%** (hard gate at 80%), covering each agent, each service's
  HTTP contract, the config loader, and the unreachable-agent error path.

## 5. Low-Level Tasks

### Task: Validation Agent

Task: Validation Stage
Prompt: "Create pipeline/validator.py with process_transaction(record: dict) -> dict.
         Check transaction_id/amount/currency/timestamp presence. Parse amount to
         decimal.Decimal; reject if unparseable or zero, and reject negatives unless
         transaction_type == 'refund'. Reject currencies not in the ISO 4217 allow-list.
         On success set status='validated'; on failure status='rejected' + reason.
         Log an audit line with masked PII."
File to CREATE: pipeline/validator.py
Function to CREATE: process_transaction(record: dict) -> dict
Details: Entry agent, no prerequisites. Terminal outcome: rejected.
         Keeps --dry-run for the /validate-transactions skill.
```

### Task: Fraud Detection Agent
```
Task: Fraud Detection Stage
Prompt: "Create pipeline/fraud_detector.py with process_transaction(record: dict) -> dict.
         Pass rejected records through untouched. Compute risk_score in [0,1] from
         +0.5 abs(amount)>10000, +0.3 hour 00:00-05:00 UTC, +0.2 metadata.country!='US',
         +0.1 wire_transfer; clamp to 1.0. Set status='flagged' if score>=0.5 else 'clear'.
         Log the audit line."
File to CREATE: pipeline/fraud_detector.py
Function to CREATE: process_transaction(record: dict) -> dict
Details: Weighted additive scoring; threshold 0.5. Flags but is not terminal —
         a flagged transaction still settles. Amounts handled as Decimal.
```

### Task: Settlement Agent
```
Task: Settlement Stage
Prompt: "Create pipeline/settlement.py with process_transaction(record: dict) -> dict.
         Rejected records are never settled (settled=False). Otherwise compute
         fee = amount * Decimal('0.005') and net = amount - fee, both ROUND_HALF_UP to
         2dp. Set data.fee, data.net_amount, data.settled=True and status='settled'
         unless already 'flagged' (preserve the flag). Log the audit line."
File to CREATE: pipeline/settlement.py
Function to CREATE: process_transaction(record: dict) -> dict
Details: Decimal fee (0.5%) and net. Flagged transactions settle but retain the flag.
```

### Task: Config-driven Orchestrator (HTTP transport)
```
Task: Orchestrator over HTTP
Prompt: "Rewrite orchestrator.py to read pipeline-config.json for the agent order and
