> Author: Mykola Bernadskyi

---

## 1. High-Level Objective

Process raw bank transactions through a sequential, file-based pipeline that
validates each record, scores it for fraud risk, and settles the non-rejected
ones — writing auditable outcomes to `shared/results/`.

---

## 2. Mid-Level Objectives

Each objective is concrete and testable:

1. **Validation gate** — a transaction is accepted only if it has all required
   fields, a parseable non-zero `Decimal` amount (negative permitted **only**
   for `transaction_type == "refund"`), and an ISO 4217 currency code.
   Everything else is rejected with a human-readable `reason`
   (e.g. TXN006 `XYZ` → `"currency 'XYZ' is not a valid ISO 4217 code"`).
2. **High-value fraud flagging** — any transaction with an absolute amount
   greater than **$10,000** contributes to its risk score and, combined with
   other signals, is flagged (`status = "flagged"`) when the score ≥ **0.5**
   (e.g. TXN002 $25k and TXN005 $75k are flagged).
3. **Multi-signal risk scoring** — the fraud stage produces a `risk_score`
   in `[0.0, 1.0]` from at least three signals: high value, off-hours activity
   (00:00–05:00 UTC, e.g. TXN004 at 02:47), and cross-border (`country != "US"`).
4. **Auditable results** — every processed transaction (accepted or rejected)
   lands in `shared/results/` as a JSON record carrying its final `status`,
   `risk_score`, settlement figures (when applicable), and a `reason` when
   rejected.
5. **Structured audit logging** — every stage emits a log line with an ISO 8601
   timestamp, stage name, transaction ID, and outcome, and never logs PII
   (account numbers/names) in plaintext.

---

## 3. Implementation Notes

- **Monetary values:** parse amounts from their string form into
  `decimal.Decimal`. Never use `float` for amount, fee, or net calculations.
  Round monetary results with `ROUND_HALF_UP` to 2 decimal places.
- **Currency codes:** validate against an ISO 4217 allow-list
  (at minimum USD, EUR, GBP, JPY; extendable). Reject anything else.
- **Timestamps:** ISO 8601 in UTC with a trailing `Z`
  (e.g. `2026-03-16T10:00:00Z`). Parse for the off-hours fraud signal.
- **Logging / audit trail:** one structured line per stage per transaction —
  `timestamp | stage | transaction_id | outcome`. Mask PII: log
  `ACC-1***` rather than the full account number; never log names.
- **PII:** `source_account`, `destination_account`, and any name-like field are
  sensitive. They pass through the pipeline data but must not appear in logs.
- **File-based hand-off envelope:** stages exchange JSON message files with the
  shape below; they never import or call each other directly.

  ```json
  {
    "message_id": "uuid4-string",
    "timestamp": "2026-03-16T10:00:00Z",
    "source_stage": "validator",
    "target_stage": "fraud_detector",
    "message_type": "transaction",
    "data": {
      "transaction_id": "TXN001",
      "amount": "1500.00",
      "currency": "USD",
      "status": "validated"
    }
  }
  ```

## 4. Context

### Beginning state
`sample-transactions.json` — a list of 8 raw transaction records. Each record:

| Field | Type | Notes |
|-------|------|-------|
| `transaction_id` | string | e.g. `TXN001` |
| `timestamp` | ISO 8601 string | UTC, `Z` suffix |
| `source_account` | string | PII — do not log |
| `destination_account` | string | PII — do not log |
| `amount` | string | parse to `Decimal` |
| `currency` | string | ISO 4217 |
| `transaction_type` | string | `transfer` \| `wire_transfer` \| `refund` |
| `description` | string | free text |
| `metadata` | object | `channel`, `country` |

The set intentionally contains edge cases: an invalid currency (`XYZ`, TXN006),
a negative refund (`-100.00`, TXN007), high-value wires (TXN002, TXN005), a
boundary amount just under $10k (TXN003, `9999.99`), and an off-hours
cross-border record (TXN004).

### Ending state
- Every input transaction has a corresponding result file in `shared/results/`.
- A pipeline **summary report** (counts of validated / flagged / rejected /
  settled, plus rejection reasons) is produced for the summary report and MCP
  `pipeline://summary` resource.
- Test coverage **≥ 90%** (hard gate at 80%).

## 5. Low-Level Tasks

### Task: Validation Stage
```
Task: Validation Stage
Prompt: "Create pipeline/validator.py with process_transaction(record: dict) -> dict.
         Check that transaction_id, amount, currency, and timestamp are present.
         Parse amount to decimal.Decimal; reject if unparseable or zero, and reject
         negative amounts unless transaction_type == 'refund'. Reject currencies not
         in the ISO 4217 allow-list. On success set data.status = 'validated'; on
         failure set status = 'rejected' and data.reason to a human-readable message.
         Log an audit line (timestamp, stage, transaction_id, outcome) with masked PII."
File to CREATE: pipeline/validator.py
Function to CREATE: process_transaction(record: dict) -> dict
Details: Required-field check; Decimal parse; sign rule (negative only for refunds);
         zero rejected; ISO 4217 currency allow-list. Emits status validated|rejected
         with reason. Supports a --dry-run mode for the /validate-transactions skill.
```

### Task: Fraud Detection Stage
```
Task: Fraud Detection Stage
Prompt: "Create pipeline/fraud_detector.py with process_transaction(record: dict) -> dict.
         Skip records already rejected. Compute risk_score in [0.0, 1.0] from signals:
         +0.5 if abs(amount) > 10000; +0.3 if hour is 00:00-05:00 UTC; +0.2 if
         metadata.country != 'US'; +0.1 for wire_transfer. Clamp to 1.0. Set
         data.risk_score and status = 'flagged' if score >= 0.5 else 'clear'.
         Log the audit line."
File to CREATE: pipeline/fraud_detector.py
Function to CREATE: process_transaction(record: dict) -> dict
Details: Weighted additive scoring over high-value, off-hours, cross-border, and
         wire-transfer signals; threshold 0.5 for flagging; rejected records pass
         through untouched. Amounts handled as Decimal.
```

### Task: Settlement Stage
```
Task: Settlement Stage
Prompt: "Create pipeline/settlement.py with process_transaction(record: dict) -> dict.
         Skip rejected records (write them to results as-is). For the rest, compute
         fee = amount * Decimal('0.005') and net = amount - fee, both rounded
         ROUND_HALF_UP to 2 dp. Set data.fee, data.net_amount, and status = 'settled'
         (preserve 'flagged' as a parallel review flag). Log the audit line."
File to CREATE: pipeline/settlement.py
Function to CREATE: process_transaction(record: dict) -> dict
Details: Decimal fee (0.5%) and net computation with ROUND_HALF_UP; rejected records
         are not settled but still reach results/. Flagged transactions are settled
         but retain their flag for downstream review.
```
