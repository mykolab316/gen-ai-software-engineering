---

## 1. High-Level Objective

Process raw bank transactions through a set of **order-independent, file-based
agents** — validation, configurable compliance screening, fraud scoring, and
settlement — that converge to a stable outcome regardless of execution order,
and expose the whole pipeline over a **REST API** so transactions can be
submitted and results retrieved via HTTP.

---

## 2. Mid-Level Objectives

Each objective is concrete and testable:

1. **Validation gate** — a transaction is accepted only if it has all required
   fields, a parseable non-zero `Decimal` amount (negative permitted **only**
   for `transaction_type == "refund"`), and an ISO 4217 currency code.
   Everything else is `rejected` with a human-readable `reason`
   (e.g. TXN006 `XYZ` → `"currency 'XYZ' is not a valid ISO 4217 code"`).
2. **Configurable compliance screening** — a `compliance` agent blocks a
   transaction (`status = "blocked"` + `reason`) when it violates a rule loaded
   from `rules.json`: a denied country (`metadata.country` in `deny_countries`),
   an amount over `max_amount`, or a `source_account`/`destination_account` in
   `denied_accounts`. Rules are data, not code: changing `rules.json` changes
   behavior with **no code change**. The default `rules.json` is permissive so
   the existing 8-sample outcomes do not regress.
3. **Multi-signal fraud scoring** — the fraud agent produces a `risk_score` in
   `[0.0, 1.0]` from additive signals — high value (abs amount > **$10,000**),
   off-hours (00:00–05:00 UTC, e.g. TXN004 at 02:47), cross-border
   (`country != "US"`), and `wire_transfer` — and sets `status = "flagged"`
   when the score ≥ **0.5** (e.g. TXN002 $25k, TXN005 $75k).
4. **Order-independent convergence** — agents guard on prerequisites and a
   terminal status, are idempotent, and **defer** (no-op) when prerequisites are
   unmet. Running the four agents in **any order** to a fixpoint yields
   identical `shared/results/` for the same input (settlement never finalizes a
   record before validation, compliance, and scoring have run).
5. **REST API gateway** — transactions are submitted (`POST /api/transactions`)
   and results retrieved (`GET /api/transactions/{id}`) purely over HTTP;
   unknown ids return `404`, malformed bodies return `422/400`, and no client
   reads `shared/` directly. The file-based pipeline is unchanged internally —
   the API is a wrapper.
6. **One-shot demo** — `./demo.sh` starts the API, submits a set of test
   transactions (including a blocked and a rejected case), retrieves and prints
   the results and summary, and cleans up — with **zero manual steps**.

## 3. Implementation Notes

- **Monetary values:** parse amounts from their string form into
  `decimal.Decimal`. Never use `float` for amount, fee, net, or the
  `max_amount` comparison. Round monetary results `ROUND_HALF_UP` to 2 dp.
- **Currency codes:** validate against an ISO 4217 allow-list (USD, EUR, GBP,
  JPY, …; extendable). Reject anything else.
- **Timestamps:** ISO 8601 in UTC with a trailing `Z` (e.g.
  `2026-03-16T10:00:00Z`). Parse for the off-hours fraud signal.
- **Logging / audit trail:** one structured line per agent per transaction —
  `timestamp | stage | transaction_id | outcome`. Mask PII: log `ACC-1***`
  rather than the full account number; never log names.
- **PII:** `source_account`, `destination_account`, and any name-like field are
  sensitive. They pass through the pipeline data but must not appear in logs.
- **Rule engine (`rules.json`):** JSON only (stdlib, no new dependency). Loaded
  once per run with safe defaults when the file is missing/partial. Shape:

  ```json
  {
    "deny_countries": [],
    "denied_accounts": [],
    "max_amount": null
  }
  ```

  Empty lists and `null` mean "no restriction" (the permissive default). Tests
  and `demo.sh` supply stricter rules to exercise blocking.

- **Agent contract (guard + defer + idempotent):** every agent is
  `process_transaction(record: dict) -> dict` and, on each call:
  1. **short-circuits** on a terminal status (`rejected`, `blocked`, or already
     `settled`) — returns the record unchanged;
  2. **is idempotent** — if it has already applied (its marker field is
     present), it no-ops;
  3. **defers** (returns unchanged) if its **prerequisites** are not yet met;
  4. otherwise applies its logic and records a marker field.

  | Agent | Prerequisites | Marker set | Terminal outcome |
  |-------|---------------|------------|------------------|
  | `validator` | none | `validated` | `rejected` |
  | `compliance` | `validated == true` | `compliant` | `blocked` |
  | `fraud_detector` | `validated` & `compliant` | `risk_score` | (flags, not terminal) |
  | `settlement` | `validated` & `compliant` & scored | `settled` | `settled` |

- **Convergence:** the orchestrator sweeps all agents over every pending record
  repeatedly until a full sweep changes nothing (fixpoint). Because each agent
  only advances state monotonically, the fixpoint is reached in at most *N*
  sweeps (*N* = number of agents) and is independent of agent order.

- **File-based hand-off envelope:** agents exchange JSON message files with the
  shape below; they never import or call each other directly.

  ```json
  {
    "message_id": "uuid4-string",
    "timestamp": "2026-03-16T10:00:00Z",
    "source_stage": "compliance",
    "target_stage": "fraud_detector",
    "message_type": "transaction",
    "data": {
      "transaction_id": "TXN001",
      "amount": "1500.00",
      "currency": "USD",
      "status": "validated",
      "validated": true
    }
  }
  ```

- **REST gateway:** FastAPI wraps the pipeline. `POST` validates the body with a
  Pydantic model, writes the record into the pipeline via an orchestrator
  `process_one(record)` (runs the agents to fixpoint for that single record,
  **without** wiping `shared/`), and returns the final result. Submissions are
  idempotent on `transaction_id`. Retrieval reads results **through the API**,
  never by exposing the filesystem. Existing `POST /api/run` and
  `GET /api/results` are kept as thin back-compat shims for the dashboard.

## 4. Context

### Beginning state
- `sample-transactions.json` — a list of 8 raw transaction records. Each record:

  | Field | Type | Notes |
  |-------|------|-------|
  | `transaction_id` | string | e.g. `TXN001` |
  | `timestamp` | ISO 8601 string | UTC, `Z` suffix |
  | `source_account` | string | PII — do not log |
  | `destination_account` | string | PII — do not log |
  | `amount` | string | parse to `Decimal` |
  | `currency` | string | ISO 4217 |
  | `transaction_type` | string | `transfer` \| `wire_transfer` \| `refund` |
  | `description` | string | free text |
  | `metadata` | object | `channel`, `country` |

  Edge cases: invalid currency (`XYZ`, TXN006), negative refund (`-100.00`,
  TXN007), high-value wires (TXN002, TXN005), a boundary amount just under $10k
  (TXN003, `9999.99`), and an off-hours cross-border record (TXN004).
- `rules.json` — compliance policy (default permissive; see §3).

### Ending state
- Every processed transaction has a result retrievable via the REST API and a
  corresponding file in `shared/results/` carrying its final `status`
  (`settled` / `flagged` / `rejected` / `blocked`), `risk_score`, settlement
  figures, and a `reason` when not passed.
- A pipeline **summary report** (counts by status, plus rejection/block reasons)
  is produced for the summary file, the `GET /api/summary` endpoint, and the MCP
  `pipeline://summary` resource.
- `demo.sh` runs end-to-end with no manual steps.
- Test coverage **≥ 90%** (hard gate at 80%), including the new agent, the rule
  engine, order-independence, and the API endpoints.

         fee=amount*Decimal('0.005') and net=amount-fee (ROUND_HALF_UP, 2dp), set data.fee,
